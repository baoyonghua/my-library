# 一致性与事务

事务边界、远程调用、本地消息表、缓存、幂等的规则都在这里。示例省略 package 和 import。

## 1. 事务边界

| 范围                        | 一致性     | 手段                                                      |
|-----------------------------|------------|-----------------------------------------------------------|
| 单个聚合的写入              | 强一致     | Repository 实现的一个方法内开一个本地事务                 |
| 同一领域内的多个聚合        | 最终一致   | 领域服务分步调用各自的 Repository 方法，每步幂等          |
| 跨领域                      | 最终一致   | Case 依次编排，每步幂等，配合重试或补偿                   |
| 外部系统（RPC / HTTP / MQ） | 最终一致   | 事务外经 Port 调用；需要可靠发送 MQ 时用本地消息表（第 3 节） |
| Redis、ES 等非事务存储      | 不参与事务 | 提交后写入，或失败时补偿，用 TTL / 对账兜底               |

- `@Transactional(rollbackFor = Exception.class)` 只加在 Repository 实现的方法上，一个方法就是一次完整的聚合写入。事务一旦上移到领域服务或
  Case，Port 调用和 Redis 操作就很容易被一起包进去。
- 同一个类内部的方法互相调用不经过 Spring 代理，不会开新事务；不要在 Repository 内嵌套调用另一个事务方法来"拆事务"。
- 事务方法里不吞异常，否则事务不会回滚。

## 2. 事务内不做远程调用

远程调用无法随本地事务回滚，还会拉长事务、占用连接和行锁。

- "调外部 + 写库"：拆成"本地事务 → 事务外调用 → 本地事务"，第一步落一条状态为处理中的记录，调用结果不明时由对账任务查证。
- "写库 + 发送 MQ"：用本地消息表，见第 3 节。

## 3. 写库后可靠发送消息

写库之后要发 MQ 消息时，不能在事务里发（业务回滚了消息却已发出），也不能提交后直接发（发送前进程崩溃，消息就丢了）。用本地消息表（Outbox）：

- **同事务写入**：消息和业务数据在同一个本地事务里写入本地消息表，业务回滚时消息也不存在；消息表和业务表必须在同一个库。
- **由领域决定发什么**：消息的类型和内容由聚合工厂或领域服务创建，随聚合交给 Repository，在业务 Repository 的同一个事务方法里写入；Repository 不自己拼消息。
- **提交后发送**：事务提交后可以立即发送一次；失败或进程崩溃由定时任务扫描重发，直到 MQ 确认成功（同步发送并检查 broker 的返回，异步、oneway 发送不能当作成功）。
- **全服务共用一套**：本地消息表和发送、重试组件与业务无关，整个服务只有一套，业务领域不各自建表、建 Port、建重试任务。具体实现按工程已有方案；工程还没有时，先和用户确认方案再实现。
- **至少一次、不保证顺序**：消费方必须按消息 ID 幂等，并能处理乱序到达。
- **消息体保持精简**：只放标识和少量字段，消费方需要更多数据时按业务单号回查。

## 4. 缓存与 Redis

- 写库后的缓存删除放在事务提交之后（`TransactionSynchronization#afterCommit`），读时回填，TTL 兜底；不要在事务内写缓存，否则回滚后缓存里留下不存在的数据。
- Redis key 由 Repository 实现拼接，领域层只传业务标识。一致性要求高的数据不要缓存。

## 5. 幂等

最终一致依赖重试，所以每一步都必须能安全地重复执行：

- 常用手段：条件更新（`WHERE status = 'CREATE'`）、唯一键（订单号、消息 ID）、按业务号去重。
- 影响行数在 Repository 内校验：0 行抛 `BusinessException`；约定为幂等空操作的方法（如重复的支付回调）返回 `false`，并在接口注释写明。

## 6. 反模式

```java
// ❌ 事务内调用外部服务：库存服务、通知服务不会随数据库事务回滚
@Transactional
public void placeOrder(OrderAggregate aggregate) {
    inventoryService.deduct(aggregate.getItems());
    repository.save(aggregate);
    notificationService.send(aggregate);
}
// ✅ 事务只包住本地写入，消息写进同一事务的本地消息表，发送放在提交之后

// ❌ 在领域服务或 Case 上加 @Transactional，想用一个事务包住多个领域或多个步骤
// ✅ 事务只在 Repository 方法内；跨步骤、跨领域用最终一致，每步幂等

// ❌ 先提交业务，再单独写消息表：两步之间进程崩溃，消息永远丢失
// ✅ 消息在业务 Repository 的同一个 @Transactional 方法里写入

// ❌ @Transactional 方法内 catch 所有异常并返回失败结果：事务永远不会回滚
// ✅ 让异常抛出；需要返回失败结果时在事务方法外层转换
```
